# 小智 XiaoZhi - 后端技术评估文档

## 一、技术选型

| 组件 | 选择 | 理由 |
|------|------|------|
| 后端框架 | Node.js (NestJS) | 生态丰富，插件系统对接MCP协议方便 |
| 沙箱方案 | Node.js 进程级沙箱 | vm2/SecureVm + 权限控制，放弃 Docker |
| 向量库 | 插件化架构 | 默认 pgvector（轻量），后续可切换 Milvus/Chroma/Qdrant |

---

## 二、功能模块复杂度分级

| 复杂度 | 模块 | 说明 |
|--------|------|------|
| **低** | 智能体管理 | CRUD操作，无特殊技术难点 |
| **中** | AI对话引擎（基础） | 多模型接入、SSE流式输出有成熟方案 |
| **中** | 工作区管理 | 文件索引需结合向量库，但实现路径清晰 |
| **中** | 记忆系统 | Redis会话 + pgvector向量检索，有章可循 |
| **中** | 知识库系统 | 文档解析+向量化+RAG，方案成熟 |
| **中** | 插件沙箱隔离 | vm2 + 权限控制，比Docker简单 |
| **高** | 插件系统（协议适配） | MCP/A2A协议需深入研究实现 |
| **高** | Agent编排引擎 | 任务规划、评分选择机制需AI能力配合 |

---

## 三、技术可行性分析

### 可行（已有成熟方案）

| 模块 | 方案 | 说明 |
|------|------|------|
| SSE流式输出 | NestJS + `ai` SDK 或 `readline` | 方案成熟 |
| 多模型接入 | 统一抽象接口 + OpenAI/Claude API适配器 | 易于扩展 |
| 对话管理 | PostgreSQL存储会话 + Redis缓存上下文 | 经典组合 |
| 记忆系统 | 会话级Redis，跨会话PG；向量检索pgvector | 轻量高效 |
| RAG检索 | pgvector + 混合检索 | 开源参考多 |
| 操作审查 | 五级分类 + 审批流，逻辑实现 | 难度不高 |
| MCP协议 | `@modelcontextprotocol/sdk` | 官方Node.js SDK |

### 有挑战需专项研究

| 模块 | 挑战 | 应对 |
|------|------|------|
| MCP协议完整支持 | 协议细节复杂 | 优先核心工具调用，完整协议放后期 |
| vm2沙箱 | Windows环境兼容性 | 验证vm2在目标环境的表现 |
| 工作区文件语义索引 | 需持续集成文件监控 | 增量向量化方案 |

## 五、关键风险点

| 风险 | 影响 | 建议 |
|------|------|------|
| MCP协议实现 | 协议细节复杂，可能延期 | 优先实现核心工具调用，完整协议放后期 |
| 沙箱隔离 | vm2在Windows环境可能有兼容问题 | 提前POC验证，准备备选方案（isolated-vm） |
| 向量检索性能 | 大规模文档可能成瓶颈 | 前期pgvector轻量方案，后续可迁移Milvus |
| 任务规划成本 | 频繁LLM调用成本高 | 引入缓存+节流机制 |

---

## 六、MCP协议实现建议

使用官方 Node.js SDK `@modelcontextprotocol/sdk`：

```
npm install @modelcontextprotocol/sdk
```

已有完整实现：
- **MCP Host**：连接外部 MCP Server
- **MCP Server**：暴露工具给外部

可大幅降低协议实现复杂度。
